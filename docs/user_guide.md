# User's guide

## ActivityPub

To use microblog.pub well, you need to know a bit about how [ActivityPub](https://activitypub.rocks/) works.

Skimming the [Overview section of the ActivityPub specification](https://www.w3.org/TR/activitypub/#Overview) is enough.

The **Fediverse** is the common name for all the interconnected/federated instances of servers supporting ActivityPub (like Mastodon, Pleroma, PeerTube, PixelFed...).

## Mastodon client apps

Besides the built-in web UI, you can use your instance from any Mastodon
client app (Tusky, Fedilab, Ivory, the official Mastodon app...): enter your
domain where the app asks for an instance, then log in with your admin
password. See the dedicated [Mastodon client apps](mastodon_api.md) page for
what's supported, what isn't, and troubleshooting tips.

## Configuration

### Profile

The setup wizard generates your initial profile configuration.

You can edit the configuration file stored in `data/profile.toml` ([TOML](https://toml.io/en/)) by hand. You cannot change the following config items without breaking federation, since they define your ActivityPub handle `@handle@domain`:

 - `domain`
 - `username`

You can tweak your profile with these items:

 - `name`: The name shown with your profile.
 - `summary`: The summary or 'bio' part of your profile, written in Markdown.
 - `about`: An optional, longer introduction written in Markdown, shown on the autogenerated `/about` page and as the Mastodon client API's "extended description". Falls back to `summary` when unset.
 - `icon_url`: Your profile image or avatar.
 - `image_url`: A 'header' or 'banner' image. The default Microblog.pub templates don't show it. Mastodon (which uses a 3:1 ratio image) and Pleroma use it. Pixelfed and Peertube, for example, don't show these images by default.

When you update one of these config items, microblog.pub sends an `Update` activity to all known servers to update your remote profile.

Restart the server for changes to take effect.

Before restarting the server, you can check for mistakes by running the [configuration checking task](#configuration-checking).

microblog.pub itself doesn't use `image_url` anywhere yet, but other clients/servers sometimes show it as a background image on remote profiles.
You _can_ use this image in microblog.pub by adding this:

```html
<img src="{{ local_actor.image_url | media_proxy_url }}">
```

to an appropriate place of your template (most likely, `header.html`).
See the section about [custom templates](#custom-templates) for more information.

#### Local avatar/header files

If you'd rather not host your avatar/header elsewhere and reference it with an
absolute URL, you can drop image files into the instance and let it
serve them. The avatar and header are resolved in this priority order:

1. **`icon_url` / `image_url` in `data/profile.toml`**: an explicit URL here
   always wins. If set, the files below are ignored.
2. **`data/avatar.jpg` / `data/profile.image.jpg`**: your own files, kept with
   the rest of your mutable data (and so preserved across upgrades and
   Docker image rebuilds).
3. **`app/static/avatar.jpg` / `app/static/profile.image.jpg`**: packaged
   defaults shipped with the instance; a `data/` file of the same name overrides
   them.

When one of these files is used, the instance serves it from `/img/avatar.jpg` (or
`/img/profile.image.jpg`) on your own domain, and advertises that URL as your
`icon`/`image` over ActivityPub and as the `og:image` meta tag. `/img/` serves only
three exact filenames: these two and [`favicon.ico`](#custom-favicon). As with any profile
change, restart the server for it to take effect (an `Update` activity is then
federated to known servers).

`/img/` responses carry `Cache-Control: max-age=31536000` (one year), so a browser that
already loaded your old avatar, header or favicon may keep showing it after the restart.
Force-reload the page or clear the browser cache to see the new file.

### Profile metadata

You can add metadata to your profile with the `metadata` config item.

Markdown is supported in the `value` field.

Most other software, like Mastodon, limits the number of key/value pairs to 4.

```toml
metadata = [
  {key = "Documentation", value = "[https://docs.microblog.pub](https://docs.microblog.pub)"},
  {key = "Source code", value = "[https://github.com/toniher/microblog.pub](https://github.com/toniher/microblog.pub)"},
]
```

### Featured tags

You can pin hashtags to your profile with the `featured_tags` config item. Mastodon
clients (Tusky, Ivory, Ice Cubes…) show these as clickable badges on your profile,
alongside how many of your posts use each tag.

```toml
featured_tags = ["microblogging", "activitypub"]
```

This is read-only: you configure featured tags in `profile.toml` and can't edit them from
a client, so only the `GET` endpoints (`/api/v1/featured_tags` and
`/api/v1/accounts/:id/featured_tags`) are implemented, not `POST`/`DELETE /api/v1/featured_tags`.
The public web profile shows them too, linking to the matching [hashtag
page](#public-website), and remote servers receive them as Mastodon's
`toot:featuredTags` collection (served at `/featured_tags`), so they show up on your
profile as seen from another instance.

### Discoverability

These two `profile.toml` items are published on your actor, so remote servers know
what you want done with your profile and posts. Both default to `true`, matching what
the public web profile and the shipped `robots.txt` already allow:

 - `discoverable`: may other servers list your profile in directories, suggestions
   and "who to follow" features?
 - `indexable`: may they include your posts in full-text search?

```toml
discoverable = false
indexable = false
```

A remote server is free to ignore these requests, and they don't stop anyone from
reading a public page. Set them to say what you want; keep posts non-public if you
need it guaranteed. Both are also reported to Mastodon clients
(as `discoverable` and `noindex` on the account), and microblog.pub honours the same
properties on remote actors when they publish them.

### Followers and following

These `profile.toml` items control how followers are handled and what's shown
publicly (all default to `false`):

 - `manually_approves_followers`: require manual approval of new followers.
 - `hides_followers`: hide your followers list.
 - `hides_following`: hide who you are following.

```toml
manually_approves_followers = true
hides_followers = true
hides_following = true
```

When a list is hidden, visitors who aren't logged in as admin:

 - get a 404 on the public `/followers` (or `/following`) page;
 - don't see its count in the header or on `/about`;
 - get only the total count from the ActivityPub collection, without the actor list.

You still see both lists and counts while logged in.

### Quote posts

When a remote server asks to quote one of your posts (FEP-044f), the `quote_policy`
config item controls how the request is handled:

```toml
quote_policy = "public"
```

 - `"public"` (the default): auto-accept a request targeting a public or unlisted
   post, reject anything else.
 - `"followers"`: like `"public"`, but the requester must also be one of your
   followers.
 - `"manual"`: each request shows up as a notification with accept/reject
   buttons, like an incoming follow request. You can't turn this one off via
   `disabled_notifications`, for the same reason as a pending follow request:
   it's the only place to act on it.
 - `"nobody"`: always reject.

When you quote someone else's post, microblog.pub first sends their server a request
(quoting your own post needs no request); the status stays pending
until they respond. The handshake is [FEP-044f][fep-044f]: a `QuoteRequest` the
other server answers with an `Accept` (carrying an authorization stamp) or a
`Reject`. The stamp matters beyond the pending state: Mastodon 4.5 and later
refuse to display a quote without one.

You can revoke a stamp you've granted for one of your own posts from `/admin`, with the
**revoke quote** button next to the quoting post and next to its notification. That
sends the quoting server a `Delete` of the stamp and stops the quote rendering here
at once, but reaching everyone who already saw the quote depends on that server
forwarding the revocation to its own audience, as the FEP describes.

[fep-044f]: https://codeberg.org/fediverse/fep/src/branch/main/fep/044f/fep-044f.md

### URL aliases

Every post is reachable at an opaque permalink like `/o/ef0166f89a124e7d9d3d6305cfa5597a`.
From the composer's **More options** or a post's admin **edit** page, you can give it a human-readable alias instead:
set it and the post's canonical URL becomes `/post/my-first-note`; the old
`/o/…` link keeps working, redirecting (301) to the alias. Clearing the alias field
restores the original URL. This is local-only: changing only the alias does not
federate an `Update` to followers.

The alias you type is normalized: lowercased, spaces collapsed into hyphens, and
anything other than a letter, digit, hyphen or underscore stripped, so
`My First Note!` becomes `my-first-note`. Prefer hyphens over underscores for
word separation (`my-first-note`, not `my_first_note`): the normalization produces
hyphens, and the app's own URLs use them elsewhere. Aliases are capped at 200 characters and must be
unique across all posts, including deleted ones.

The path prefix (`post` by default) is configurable via the `alias_url_prefix`
config item in `profile.toml`:

```toml
alias_url_prefix = "blog"
```

It must not collide with an existing top-level route. The config check rejects
`o`, `t`, `e`, `articles`, `about`, `admin`, `inbox`, `outbox`, `followers`,
`following`, `featured`, `featured_tags`, `img`, `proxy`, `attachments`, `static`,
`nodeinfo`, `remote_follow`, `remote_interaction`, `feed.json`, `feed.rss`,
`feed.atom`, `robots.txt`, `.well-known`, `custom_emoji`, `openapi.json`, `api`,
`auth`, `oauth`, `token`, `revoke_token`, `token_introspection`, `micropub` and
`webmentions`, and the server refuses to start with one of them. Treat it as a
set-once setting: changing it after posts have been aliased and federated
invalidates the `url` already sent to remote servers for those posts (local
rendering picks up the new prefix at once, and `/o/{public_id}`, the
ActivityPub `id`, which never changes, keeps resolving either way).

### Default language

You can set a default language for your instance with the `language_code` config item in
`profile.toml`, using a [BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag) tag
(e.g. `en`, `fr`, `pt-BR`):

```toml
language_code = "en"
```

The default value is `en`. microblog.pub uses it for the `lang` attribute of the generated HTML pages
(which helps screen readers and translation tools) and as the example in the
placeholder of the [per-note language](#authoring-notes) field.

It is also the fallback language for the **interface** (buttons, labels, messages):
both the admin UI (`/admin`) and public pages use a visitor's browser
language when a translation is available for it, falling back to `language_code`
otherwise (e.g. no `Accept-Language` header sent, or none of the requested languages
are available). See the [developer guide](developer_guide.md#translations-i18n) for
how translations are added.

### Schema.org microdata

By default, the generated HTML only carries [microformats2](https://microformats.org/wiki/microformats2)
markup. You can also enable [schema.org](https://schema.org) structured data
(`itemscope`/`itemtype`/`itemprop` microdata attributes) with:

```toml
enable_microdata = true
```

The default value is `false`. When enabled, feeds are marked up as a `Blog`, and each
note/article/video/event as the corresponding schema.org type (`BlogPosting`,
`SocialMediaPosting`, `VideoObject`, `Event`…), with `author`, `datePublished`, `url`
and media properties filled in alongside the existing microformats2 classes. Search
engines and other tools that read schema.org structured data (e.g. rich results) can
use it to understand your content.

### Privacy replace

You can define domains to be rewritten to more "privacy friendly" alternatives, like [Invidious](https://invidious.io/)
or [Nitter](https://nitter.net/about).

To do so, add these extra config items. This sample config rewrites URLs for Twitter, Youtube, Reddit and Medium:

```toml
privacy_replace = [
    {domain = "youtube.com", replace_by  = "yewtu.be"},
    {domain = "youtu.be", replace_by  = "yewtu.be"},
    {domain = "twitter.com", replace_by = "nitter.fdn.fr"},
    {domain = "medium.com", replace_by = "scribe.rip"},
    {domain = "reddit.com", replace_by = "teddit.net"},
]
```

All notifications are enabled by default.

You can disable specific notifications by adding them to the `disabled_notifications` list.

This example disables likes and shares notifications:

```
disabled_notifications = ["like", "announce"]
```

### Outgoing HTTP connections

Requests the server makes to other instances (fetching ActivityPub objects, delivering
activities, webfinger lookups, and proxying remote media) go through shared HTTP
clients that keep connections alive and reuse them, negotiating HTTP/2 where the remote
end supports it.

This is on by default and needs no configuration. All four settings below are
optional; omit them to keep the default behaviour.

```toml
http_client_pooling = true
http_client_http2 = true
http_client_max_connections = 100
http_client_max_keepalive_connections = 20
```

 - `http_client_pooling`: when `false`, no connection is kept open past the response
   that used it, so each request opens a fresh one. This also disables HTTP/2, since
   running several requests over a single multiplexed connection is also a form of
   connection sharing.
 - `http_client_http2`: when `false`, connections are still pooled and reused, but only
   HTTP/1.1 is negotiated. Has no effect if `http_client_pooling` is `false`.
 - `http_client_max_connections`: upper bound on connections open at once, across all
   remote hosts.
 - `http_client_max_keepalive_connections`: how many idle connections are kept around
   for reuse.

Pooling has one visible side effect. A page's remote images usually come from a
single host, so they now share one connection and tend to finish
together, rather than trickling in one by one as they did when each request opened its
own connection. The page finishes loading sooner, but it renders in one go instead of
progressively. Setting `http_client_pooling = false` restores the old behaviour at the
cost of re-establishing a connection for every request.

### Outgoing federation delivery

Activities queued for delivery (to followers, mentioned actors, webmention targets…) are
sent out in batches, with several deliveries in flight at once instead of one at a time.

This is on by default and needs no configuration. All three settings below are
optional; omit them to keep the default behaviour.

```toml
outgoing_delivery_batch_size = 20
outgoing_delivery_concurrency = 10
outgoing_delivery_per_host_concurrency = 2
```

 - `outgoing_delivery_batch_size`: how many due activities are fetched per poll.
 - `outgoing_delivery_concurrency`: how many deliveries run at once, across all
   recipients. Must not exceed `http_client_max_connections`.
 - `outgoing_delivery_per_host_concurrency`: how many deliveries run at once against a
   single remote host. Must not exceed `outgoing_delivery_concurrency`.

These values never change the delivery order to a given recipient inbox: activities
queued for the same inbox are still delivered one at a time, in order, so a boost can
never overtake the post it boosts, for example. Only deliveries
to *different* recipients run concurrently. Setting `outgoing_delivery_concurrency = 1`
restores serial delivery, one activity at a time.

### Upload size limits

All settings below are optional; omit them to keep the defaults, which match what's
advertised to Mastodon clients out of the box.

```toml
max_image_upload_size = 10485760  # 10 MiB
max_video_upload_size = 41943040  # 40 MiB
max_image_pixels = 16777216       # 16 MP
```

 - `max_image_upload_size`: the largest an image upload may be, in bytes.
 - `max_video_upload_size`: the largest a video *or audio* upload may be, in bytes
   (audio shares this limit rather than getting a third setting, matching Mastodon).
 - `max_image_pixels`: the largest an image upload may be in *pixels* (width × height).

The pixel cap covers what the byte cap misses: a 7 MB JPEG straight off a phone
decodes to a 12 megapixel bitmap, and EXIF-stripping and thumbnailing both cost memory
and CPU in proportion to pixel count, not file size. microblog.pub checks the limit from
the image header, before decoding any pixel, so rejecting an oversized image costs nothing.

A file over its limit is rejected before any of it is written to disk. If you're behind a
reverse proxy, make sure its own body-size cap (e.g. nginx's `client_max_body_size`, see
[Reverse proxy](install.md#reverse-proxy)) is at least as large, or it will reject a
large-but-valid upload before the app sees it.

### Web Push delivery

Mastodon client apps that support push notifications (see
[Mastodon client apps](mastodon_api.md)) are served by a separate `push_worker`
process. Both settings below are optional; omit them to keep the defaults.

```toml
vapid_key_path = "data/vapid_key.pem"
push_delivery_batch_size = 10
```

 - `vapid_key_path`: where the instance's VAPID (RFC 8292) keypair lives. Generated
   on first use; back it up along with the rest of `data/`. Regenerating
   it invalidates all existing subscriptions, and clients must re-subscribe.
 - `push_delivery_batch_size`: how many subscriptions with pending notifications are
   fetched per poll by the `push_worker` process.

### Streaming API

Mastodon client apps that support live timeline/notification updates (see
[Mastodon client apps](mastodon_api.md)) connect over `wss://…/api/v1/streaming`.
Unlike Web Push, this needs no separate process (the linked page explains why).
All settings below are optional; omit them to keep the defaults.

```toml
streaming_enabled = true
streaming_poll_interval = 1.0
streaming_max_connections = 32
```

 - `streaming_enabled`: set to `false` to disable the endpoint; this also
   removes the `streaming_api`/`configuration.urls.streaming` advertisement, so
   clients never attempt a connection that would fail.
 - `streaming_poll_interval`: how often (seconds) the in-process pump checks for
   new activity while at least one client is connected. Lower is more responsive
   and costs a few more cheap queries per second; it costs nothing when no
   client is connected.
 - `streaming_max_connections`: a cap on concurrent streaming sockets, since
   `public`/`hashtag` streams can be reached without authentication.

### Other settings

```toml
contact_email = "me@example.com"
csrf_token_exp = 3600
```

 - `contact_email`: shown on `/about`, reported as the contact address by the Mastodon
   instance API, and sent as the VAPID contact (`mailto:`) with Web Push deliveries.
   Unset by default.
 - `csrf_token_exp`: how long (seconds) an admin form stays valid after you load it.
   Default `3600`. Submitting an older form fails with "The security token has expired";
   reload the page and try again.
 - `secret`: generated by the setup wizard and used to sign admin sessions, CSRF tokens
   and media proxy URLs. Changing it logs you out, breaks any open admin form, and
   invalidates every proxied media URL already handed out.
 - `debug`: defaults to `false`. **Never enable it in production.** It turns off the
   SSRF guard on outgoing requests (so the server will fetch `localhost`, private IP
   ranges and `.onion` hosts), drops the `Strict-Transport-Security` header, logs every SQL
   statement and switches logging to `DEBUG`. It exists to test federation against
   local instances.

### Customization

#### Default emoji

If you don't like cats, or need more emoji, add your favorite emoji in `profile.toml` to replace the default ones:

```
emoji = "🙂🐹📌"
```

You can copy/paste them from [getemoji.com](https://getemoji.com/).

#### Custom emoji

You can add custom emoji in the `data/custom_emoji` directory and microblog.pub picks them up.
Filenames may only contain letters, numbers, and the underscore `_`.

#### Custom CSS

The CSS is written with [SCSS](https://sass-lang.com/documentation/syntax).

You can override colors and the font by editing `data/_theme.scss`:

```scss
$primary-color: #e14eea;                                                                            
$secondary-color: #32cd32;
```

The following variables are available to override (see `app/scss/main.scss` for the
authoritative list and their default values):

| Variable | Purpose |
| --- | --- |
| `$font-stack` | Font family used across the site |
| `$background` | Page background |
| `$light-background` | Alternate/secondary background (e.g. cards) |
| `$text-color` | Main body text |
| `$primary-color` | Primary accent (links, default favicon) |
| `$secondary-color` | Secondary accent |
| `$muted-color` | Muted/secondary text (e.g. timestamps) |
| `$form-background-color` | Form field background |
| `$form-text-color` | Form field text |
| `$nav-button-background-color` | Navigation button background |
| `$nav-button-text-color` | Navigation button text |
| `$primary-button-text-color` | Text on primary buttons |
| `$code-highlight-background` | Background behind highlighted code blocks |
| `$code-highlight-text` | Text in highlighted code blocks |
| `$diff-ins-background` / `$diff-ins-color` | Added text in the [revision diff](#post-actions) |
| `$diff-del-background` / `$diff-del-color` | Removed text in the revision diff |
| `$shadow-color` | Box shadows |

Only set the variables you want to change; anything you leave out keeps its default.
To go further than variables, add arbitrary SCSS after the variable
definitions in `data/_theme.scss`.

The palette is exposed as CSS custom properties, so the site follows the
visitor's system light/dark preference (`prefers-color-scheme`). Every variable above
except `$font-stack` and `$code-highlight-text` has a dark-mode counterpart prefixed
with `$dark-` (e.g. `$dark-background`, `$dark-text-color`, `$dark-diff-ins-color`) that
you can override the same way. `$dark-code-highlight-background` defaults to the light
`$code-highlight-background`, so code blocks stay light and Pygments colors stay
readable. Leave them unset to keep the built-in dark theme:

```scss
$dark-background: #101418;
$dark-primary-color: #6fd06f;
```

After any CSS change, [recompile CSS](#recompiling-css-files) (to update the CSS files) and restart microblog.pub (to update the CSS link in HTML documents with a new checksum; otherwise, browsers that downloaded the old CSS keep using it).

#### Custom favicon

By default, the microblog.pub favicon is a square of the `$primary-color` CSS color (see the section above on how to redefine CSS colors).
To use any icon you like, save it as `data/favicon.ico`.
It is served the same way as the [avatar/header images](#local-avatarheader-files): a `data/favicon.ico`
overrides the packaged `app/static/favicon.ico` default (the themed square) at
serve time, so you only need to restart microblog.pub for it to take effect, with no
recompile step. Browsers cache it for a year, so force-reload to see the change.
As with your data, it is preserved across upgrades and Docker image rebuilds.

#### Custom footer

By default, the footer shows a "Powered by microblog.pub" line.
You can replace it with your own text by adding a `custom_footer` config item to `profile.toml`:

```toml
custom_footer = "Content licensed under [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/), running microblog.pub {version}"
```

Markdown is supported, and the `{version}` placeholder is replaced by the running microblog.pub version.

#### Web analytics

You can add a self-hosted analytics tool such as [Matomo](https://matomo.org/),
[Plausible](https://plausible.io/), [GoatCounter](https://www.goatcounter.com/)
or [umami](https://umami.is/) by pasting the provider's tracking snippet into
the `analytics_html` config item in `profile.toml`:

```toml
analytics_html = '''
<script>
  var _paq = window._paq = window._paq || [];
  _paq.push(['trackPageView']);
  _paq.push(['enableLinkTracking']);
  (function() {
    var u = "https://analytics.example.com/";
    _paq.push(['setTrackerUrl', u + 'matomo.php']);
    _paq.push(['setSiteId', '1']);
    var d = document, g = d.createElement('script'), s = d.getElementsByTagName('script')[0];
    g.async = true; g.src = u + 'matomo.js'; s.parentNode.insertBefore(g, s);
  })();
</script>
'''
```

The snippet is inserted verbatim (as raw HTML) in the `<head>` of **public**
pages only. It never appears on `/admin` pages, or when you browse your own
instance logged in, so your own visits aren't tracked.

By default the [Content Security Policy](#custom-content-security-policy-csp)
only allows resources from your own domain (`default-src 'self'`), which
blocks a script loaded from another host. If your analytics provider is hosted
on a different domain than your instance, you also need to set
`custom_content_security_policy` to allow it, e.g.:

```toml
custom_content_security_policy = "default-src 'self'; style-src 'self' 'sha256-{HIGHLIGHT_CSS_HASH}'; script-src 'self' https://analytics.example.com; connect-src 'self' https://analytics.example.com; img-src 'self' https://analytics.example.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self';"
```

#### Custom templates

To customize your instance's theme beyond CSS, modify the app's HTML by placing templates in `data/templates`, which overwrite the defaults in `app/templates`.

A template placed in `data/templates/<name>.html` replaces `app/templates/<name>.html` entirely.
The ones you are most likely to override are:

 - `header.html`: the site header shown at the top of every public page (name, avatar, navigation)
 - `layout.html`: the overall page skeleton (`<head>`, footer, common markup)
 - `index.html`: the public homepage
 - `utils.html`: shared macros (see the per-macro override trick below)

Templates use the [Jinja](https://jinja.palletsprojects.com/en/latest/templates/) templating language.
`utils.html` also has scoped blocks around the body of each macro,
so you can override macros one at a time in `data/templates/utils.html` without copying the whole file.
For example, to override only the display of a specific actor's name/icon, create a `data/templates/utils.html` file with the following content:

{% raw %}
```jinja
{% extends "app/utils.html" %}
{% block display_actor %}
	{% if actor.ap_id == "https://me.example.com" %}
		<!-- custom actor display -->
	{% else %}
		{{ super() }}
	{% endif %}
{% endblock %}
```
{% endraw %}

#### Custom Content Security Policy (CSP)

You can override the default Content Security Policy by adding a line in `data/profile.toml`:

```toml
custom_content_security_policy = "default-src 'self'; style-src 'self' 'sha256-{HIGHLIGHT_CSS_HASH}'; frame-ancestors 'none'; base-uri 'self'; form-action 'self';"
```

This example outputs the default CSP. microblog.pub replaces `{HIGHLIGHT_CSS_HASH}` at runtime with the hash of the CSS needed for syntax highlighting.

#### Code highlighting theme

You can switch to one of the [styles supported by Pygments](https://pygments.org/styles/) by adding a line in `data/profile.toml`:

```toml
code_highlighting_theme = "solarized-dark"
```

The default is `friendly_grayscale`.

#### Custom routes

You can add custom routes in `data/custom_routes.py` (microblog.pub imports the file
at startup if it exists).

The simplest option is to serve a static HTML page. The `html_file` is read from the
`data/` directory and its content is inserted verbatim (as raw HTML) into the page
body, wrapped in the site layout:

```python
from app.customization import register_html_page

register_html_page(
    "/testcustom",
    title="test html page",
    html_file="test.html",  # relative to data/
    show_in_navbar=True,
)
```

If you register a page at `/`, it replaces the homepage, and the default stream of
notes moves to `/notes`.

For anything more dynamic, you can register a raw [FastAPI](https://fastapi.tiangolo.com/)
handler instead:

```python
from starlette.responses import PlainTextResponse
from app.customization import register_raw_handler

async def my_handler(request):
    return PlainTextResponse("hello from a custom route")

register_raw_handler(
    "/hello",
    title="Hello",
    handler=my_handler,
    show_in_navbar=False,
)
```

Routes registered with `show_in_navbar=True` (the default) get a link added to the
navigation bar.

#### Custom stream visibility

Your stream (the admin **Stream** page, and the home timeline in Mastodon apps) shows,
by default, non-reply notes from people you follow, plus anything mentioning you and
replies within your own conversations. The public homepage only lists your own posts and boosts.

You can override what appears in the stream by defining a
`custom_stream_visibility_callback` in `data/stream.py`. It receives an `ObjectInfo`
for each incoming object and returns `True` to show it in the stream or `False` to
hide it:

```python
from app.customization import ObjectInfo

def custom_stream_visibility_callback(object_info: ObjectInfo) -> bool:
    # e.g. only show posts tagged #mycommunity from people you follow
    return (
        object_info.is_from_following
        and "mycommunity" in object_info.hashtags
    )
```

The `ObjectInfo` passed to the callback exposes:

| Field | Description |
| --- | --- |
| `is_reply` | Whether the object is a reply |
| `is_local_reply` | Whether it's a reply to one of your own objects |
| `is_mention` | Whether it mentions you (the local actor) |
| `is_from_following` | Whether it's from someone you follow |
| `hashtags` | List of hashtags on the object, e.g. `["microblogpub"]` |
| `actor_handle` | The author's handle, e.g. `@dev@microblog.pub` |
| `remote_object` | The full remote object |

Restart microblog.pub after adding or changing `data/stream.py`.

### Blocking accounts

You can block a single actor from anywhere their profile is displayed in the admin
interface (the `block` button next to their handle).

The `Blocks` page in the admin menu lists every account you have blocked, with an
`unblock` button for each; it's also where you can check whether someone is still
blocked. Mastodon clients see the same list through `GET /api/v1/blocks`.

The list is ordered by when your instance first saw each account, not by when you
blocked it: blocks are stored as a flag on the account, without a timestamp of
their own.

### Muting accounts

Muting is the quieter alternative to a block: the account keeps following you and
can still see your posts, and nothing is federated (they can't tell), but their posts
stop appearing anywhere you read. That covers the stream, their boosts, *and*
other people's boosts of them, plus their notifications.

The `mute` button sits next to `block` wherever a profile is displayed in the
admin interface, and the `Mutes` page in the admin menu lists everyone you've
muted with an `unmute` button for each. Muting someone hides posts you already
received without deleting them; unmuting brings them back.

Mastodon clients see the same list through `GET /api/v1/mutes` and can mute with
the two options the API defines: whether notifications are hidden too (the admin
button always hides them), and a duration after which the mute lapses on its own
(the admin button mutes until you undo it). Like the blocks list, the page is
ordered by when your instance first saw each account, not by when you
muted it.

### Blocking servers

Besides blocking single actors via the admin interface, you can prevent any communication with entire servers.

Add a `blocked_servers` config item into `profile.toml`.

The `reason` field helps you document/remember why you blocked a server.

You should unfollow any account from a server before blocking it.

```toml
blocked_servers = [
    {hostname = "bad.tld", reason = "Bot spam"},
]
```

## Public website

Visitors see these pages:

 - `/`: your public notes, polls, videos and boosts, 20 per page, pinned posts first.
 - `/articles`: your articles (linked from the header once you have one).
 - `/about`: the `about` text (or `summary`), post/article/follower/following counts,
   your handle with a **Follow** button, and `contact_email` if set.
 - `/followers`, `/following`: the last 100 accounts each (see
   [Followers and following](#followers-and-following) to hide them).
 - `/t/{tag}`: the last 20 public posts with that hashtag.
 - `/feed.rss`, `/feed.atom`, `/feed.json`: your last 20 public notes, articles and videos.
 - A post's permalink shows up to 10 likes, 10 shares and 50 webmentions.

Fediverse users can interact without copying URLs around:

 - **Follow** (header and `/about`) asks for their handle and sends them to their own
   instance to confirm.
 - **interact from your instance** on a post page does the same for replying, liking
   or boosting that post.

You can pin up to 5 of your posts. Public pinned posts appear first on the homepage, and
remote servers read them from the `/featured` collection (Mastodon shows them as pinned on your profile).

IndieWeb apps can use your site too. The homepage advertises IndieAuth endpoints, so you
can sign in to IndieAuth-enabled sites with your domain, and a Micropub endpoint
(`/micropub`), so Micropub clients can create posts (and delete or update them, given
those scopes).

### Post actions

Each post shows a row of admin-only action buttons. Which ones appear depends on the post:

- Your own posts: `edit` (see [Editing a post](#editing-a-post)), `delete` (sends a
  `Delete` to servers that have it), `pin`/`unpin`.
- Any post: `reply`; `quote` on notes and articles.
- Posts you received: `like`/`unlike`, `bookmark`/`unbookmark`, `share`/`unshare`
  (public and unlisted posts only), `profile` (the author's admin page), and, in
  lists, `expand` (open the post with its thread).
- Replies to your posts: `local delete` removes the reply from your instance only.
- Received polls: pick your answers and vote, until the poll ends.
- `revoke quote`: see [Quote posts](#quote-posts).
- `history`: shown on your own posts once they have at least one edit. Opens a page listing
  each past revision with the timestamp it was saved at, so you can see what a post looked
  like before each edit. Each revision has a pair of radio buttons; pick a "from" and a "to"
  revision and press "Compare selected revisions" to see a word-by-word diff of what changed,
  with removed text struck through and added text underlined. Title, content warning and
  sensitive-flag changes appear alongside the body. Each row but the oldest also has
  a `prev` link (diff against the revision right before it), and each past revision has a
  `cur` link (diff against the current version).
- `fetch replies`: shown on posts from other instances that appear in your inbox (boosts and
  replies included). Fetches that post's `replies` collection from the
  remote server on demand, for replies that were never delivered to you directly. Each click is
  capped to a few seconds and a couple of new replies, so press it again if a thread
  has more replies than the first try pulled in.

### Account actions

Wherever an account appears in the admin UI (its profile page, notifications, follower
lists), you get:

- `follow`, then `undo follow` while the request is pending and `unfollow` once accepted.
- For accounts you follow: `hide shares`/`show shares` (their boosts in your stream) and
  `notify on new posts`/`don't notify on new posts` (a `status` notification for each of
  their new posts).
- `block`/`unblock` and `mute`/`unmute`: see [Blocking accounts](#blocking-accounts) and
  [Muting accounts](#muting-accounts).
- `direct message` opens the composer with their handle and Direct visibility; `mention`
  opens it with just the handle.
- `accept follow`/`reject follow` on a pending follow request (with
  `manually_approves_followers = true`), and `accept quote`/`reject quote` on a pending
  quote request (with `quote_policy = "manual"`).

## Authoring notes

The composer (**New** in the admin menu) has three tabs:

 - **Note**: a regular post.
 - **Article**: a post with a required title, listed on `/articles`.
 - **Question**: a poll. Pick single or multiple choice, a duration (5 minutes, 30
   minutes, 1 hour, 6 hours or 1 day, the default) and 2 to 4 options.

Fields:

 - **Visibility**: Public (followers and homepage), Unlisted (like public, but kept off
   the homepage), Followers only, or Direct (only the mentioned accounts). A reply starts
   with the visibility of the post it answers.
 - **Content**: [Markdown](https://commonmark.org/), with no character limit. `#hashtags`,
   `@mentions` and `:custom_emoji:` work too. A toolbar above the text area inserts
   Markdown (bold, italic, strikethrough, heading, quote, lists, inline code, code block,
   link, image), and a **Markdown formatting** cheatsheet sits below it. Ctrl/Cmd+B, I and
   K apply bold, italic and link; Ctrl+Enter publishes.
 - **Emoji picker**: inserts your [default emoji](#default-emoji) and
   [custom emoji](#custom-emoji).
 - **Content warning**: shown in place of the text until the reader expands it, and
   marks the post as sensitive. If you fill in only the content warning and attach files,
   it becomes the post text and the attachments are marked sensitive, as Mastodon does.
 - **More options**: a [URL alias](#url-aliases), the language (see below), and a
   checkbox to mark attachments as sensitive.
 - **Attachments**: pictures, video and audio, with an alt text field per file.
   microblog.pub removes EXIF metadata (like GPS location) from pictures before storing them.

You can set a **language** for the note (a [BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag)
tag such as `en` or `pt-BR`). When set, it is advertised to other servers through the
ActivityPub `contentMap`, the same way Mastodon does, so remote clients can label and filter
your post by language. The field starts empty, with your instance's
[default language](#default-language) shown only as a placeholder example; leave it empty
and the post has no language.

### Editing a post

The `edit` button on your own post opens a form where you can change:

 - the text, content warning and sensitive flag;
 - the language and URL alias;
 - the title (articles only);
 - attachments: untick **Keep** to remove one, or add new files with alt text.

You can't change the visibility, the post type or a poll's options. Saving federates an
`Update` to the servers that received the post (changing only the alias stays local).
Each edit stores a revision: use the [`history`](#post-actions) button to browse past
versions and diff them.

### Attaching video and audio

Video and audio attachments work the same way as pictures: pick a file and it uploads with the
note. There's no re-encoding: the instance serves and federates the file you upload as is,
so it must already play in mainstream browsers (Firefox/Chrome). When you pick a
video or audio file, the compose form checks it *in your browser* and shows an instant preview
(duration, dimensions) or a warning if this browser can't play it back. That check only reflects
your own browser, though (Safari plays some formats, like HEVC from an iPhone, that Firefox and
Chrome don't), so the instance also checks the file's codec/container when you
submit, and rejects it with a specific reason if it's confident the file is unsupported.

If a video or audio upload is rejected, the error names the problem (e.g. "hevc video is
not playable in most browsers"). The fix is almost always to re-encode the file as
H.264 video / AAC audio in an MP4 container, which plays everywhere. A QuickTime `.mov` container
is rejected even if the video inside is fine; remux it to `.mp4` (`ffmpeg -i in.mov -c
copy out.mp4` re-containers without re-encoding, so it's fast and lossless).

Video gets a poster frame (a still pulled from partway through the clip) shown before playback
starts, the same way an image gets a thumbnail. This requires `ffmpeg` on the
server (see [Installation](install.md)). Without it, video/audio still uploads, but without a
poster, duration, or compatibility warning (uploads are never rejected in that case).

## Interactions

microblog.pub supports the most common Fediverse interactions.

### Shares

Sharing (or announcing) an object relays it to your followers and notifies the author.
The homepage also displays it.

Most receiving servers increment the number of shares.

Receiving a share triggers a notification, increments the shares counter on the object and displays the actor avatar on the object permalink.

### Likes

Liking an object notifies the author.

Unlike shared objects, liked objects are not displayed on the homepage.

Most receiving servers increment the number of likes.

Receiving a like triggers a notification, increments the likes counter on the object and displays the actor avatar on the object permalink.

### Bookmarks

Bookmarks let you like objects without notifying the author.

A bookmark is a "private like" that lets you find the object later.

Bookmarking also prevents objects from being pruned.

### Webmentions

When you publish a public note, microblog.pub sends webmentions to ping the websites it mentions.

Receiving a webmention triggers a notification, increments the webmentions counter on the object and displays the source page on the object permalink.

## Backup and restore

All the data generated by the server is located in the `data/` directory:

 - `profile.toml`: configuration, including the `secret` and your password hash.
 - `key.pem`: your actor's HTTP Signatures key. The server won't start without it, and
   remote servers know your actor by its public half.
 - `vapid_key.pem`: the Web Push key. Losing it invalidates every push subscription, so
   Mastodon apps must re-subscribe.
 - `microblogpub.db`: the SQLite database.
 - `_theme.scss`, `templates/`, `custom_emoji/`, and the other customization files.
 - `uploads/`: uploaded media.

The database runs in WAL mode: recent writes sit in `microblogpub.db-wal` (with
`microblogpub.db-shm`) until SQLite merges them into `microblogpub.db`. Copying only the
`.db` file of a running server can give you a stale or inconsistent copy. Either:

 - stop the server (and workers) before copying `data/`, or
 - take a consistent snapshot while it runs:
   `sqlite3 data/microblogpub.db ".backup data/microblogpub.db.bak"`, and back up that file.

To restore, add your backed up `data/` directory into a fresh deployment.

### Pruning old data

Prune old data from time to time to free disk space.

The default retention for the inbox data is 15 days.

You can change it with the `inbox_retention_days` config item in `profile.toml`:

```toml
inbox_retention_days = 30
```

The task deletes, once older than `inbox_retention_days`:

 - inbox objects (and their notifications), except the ones listed below;
 - rows of the incoming and outgoing federation queues. Rows that ended in an error stay,
   so you can still debug them.

The task never deletes data owned by the server (at least for now), nor:

 - bookmarked objects
 - liked objects
 - shared objects
 - inbox objects mentioning the local actor
 - objects related to local conversations (i.e. direct messages, replies) 

For now, make a backup before running the task in case it deletes data you wanted to keep.

Shut down the server before running the task.

#### Python edition

```bash
# shutdown supervisord
cp -r data/microblogpub.db data/microblogpub.db.bak
poetry run inv prune-old-data
# relaunch supervisord and ensure it works as expected
rm data/microblogpub.db.bak
```

#### Docker edition

```bash
docker compose stop
cp -r data/microblogpub.db data/microblogpub.db.bak
make prune-old-data
docker compose up -d
rm data/microblogpub.db.bak
```

### Reporting unattached uploads

Uploaded media (images, video, audio) is stored independently of the post it's
attached to, and in a few cases a row can end up unattached to any post (e.g.
a rejected multi-file post, or media uploaded via the Mastodon API and never
used). This read-only report lists unattached `Upload` rows and files
in `data/uploads` with no matching row, but **deletes nothing**. An unattached
upload may still be needed: it can be in-flight media for a post not submitted
yet, or media queued in a scheduled post. You don't need to stop the server to
run it.

#### Python edition

```bash
poetry run inv report-unattached-uploads
```

#### Docker edition

```bash
make report-unattached-uploads
```

#### Removing a confirmed orphan by hand

The report doesn't delete anything, since an unattached upload may still be
needed (see above). If, after checking, you're sure a row is
safe to remove (e.g. an old, undated one with no `(referenced by a scheduled
status)` note, and no ongoing draft it could belong to), remove it by hand.
`data/` is the same directory in both the Python and Docker editions, so you
run this against it on the host either way:

```bash
# Back up first (safe while the server runs, unlike cp)
sqlite3 data/microblogpub.db ".backup data/microblogpub.db.bak"

# id and hash are the Upload#<id> and hash=... values the report printed
sqlite3 data/microblogpub.db "DELETE FROM upload WHERE id = <id>;"
rm -f "data/uploads/<hash>" "data/uploads/<hash>_resized"

# once you've confirmed the server still starts and behaves as expected
rm data/microblogpub.db.bak
```

For a file the report lists with no matching `Upload` row (the second half
of the report), there's nothing in the database to touch; remove the
file(s) directly.

### Deleting the instance

To delete your instance, you can ask other instances to delete your remote profile.

## Troubleshooting

If the server is not (re)starting, you can:

 - [Ensure that the configuration is valid](#configuration-checking).
 - [Check the custom theme for syntax errors by recompiling the CSS](#recompiling-css-files).
 - Look at the log files (see [Viewing logs](install.md#viewing-logs) for how they rotate
   and are compressed):
   - Docker edition: `data/uvicorn.log`, `data/incoming.log`, `data/outgoing.log` and
     `data/push.log`.
   - Python edition (`misc/supervisord.conf`): `uvicorn.log`, `incoming_worker.log`,
     `outgoing_worker.log` and `push_worker.log`, in the directory you start supervisord from.
 - Check that all four processes run: the web server (`inv uvicorn`), the incoming and
   outgoing federation workers (`inv process-incoming-activities`,
   `inv process-outgoing-activities`), and the Web Push worker
   (`inv process-push-notifications`). The supervisord configs start all four.
 - If the CSS is not working, check that your reverse proxy serves the static files correctly.
